## Решение о направлении

Продолжать имеет смысл. Полезная основа уже есть: структурный контекст, поиск, tools, configurable backends,
сохранение задач и локальная верификация. Предлагаемый первый продукт: **однопользовательский агент
для ограниченных изменений Python-проектов, с проверяемым diff, явными правами и отчётом выполнения**.
CLI/SSH — первая поверхность. Командный HTTP-сервис — отдельный следующий уровень эксплуатации.

Ценность нужно доказывать долей решённых задач при заданных расходах и качестве,
а не числом ролей, наличием графа или собственной модели.
Нужен один надёжный путь: вопрос -> контекст -> предложение изменения -> разрешённое применение
в изолированном рабочем пространстве -> независимая проверка -> diff и результат.
Обычные вопросы не должны обязательно оплачивать весь агентный конвейер.

## Корректировки исходной стратегии

| Утверждение исходного документа | Оценка |
|---|---|
| LLM-инструменты работают только с мешком файлов; структура уникальна | Слишком широкое утверждение. Aider документирует repository map и graph ranking |
| Другие инструменты проверяют только линтером | Неверное обобщение: Aider документирует автоматический запуск тестов |
| search_tree уже семантический | Сейчас лексический BM25 с graph heuristics; dense encoder отсутствует |
| Все фазы закрыты, потому что есть тесты | Подключение task теперь есть; жизненный цикл и safety properties требуют интеграционных проверок |
| Whitelist + shell=False устраняет риск произвольного кода | pytest импортирует/исполняет код проекта, включая conftest; нужна изоляция процесса/FS/сети |
| Native tool-use даст 95–98% вместо 70–85% | Здесь таких измерений нет; гипотеза для сравнительного теста |
| Encoder из enwik8 автоматически даст code semantic retrieval | Не доказано. Нужны подходящее обучение представлений и held-out retrieval evaluation |
| $0.10 за задачу — достигнутый SLA | Несколько примеров не SLA; нужны распределения и стоимость успешно решённой задачи |
| TUI/multi-agent необходимы для product-level | Для первого надёжного CLI-продукта необязательны |

Aider: [repository map](https://aider.chat/docs/repomap.html),
[автоматические lint/test](https://aider.chat/docs/usage/lint-test.html).
Изоляция FS и сети как границы агентного исполнения:
[инженерное описание Anthropic](https://www.anthropic.com/engineering/claude-code-sandboxing).
Отдельное обучение и оценка embeddings:
[Sentence Transformers training overview](https://sbert.net/docs/sentence_transformer/training_overview.html).
Вывод о пригодности именно atomic-core остаётся нашей исследовательской гипотезой; его веса здесь не оценивались.

## Последовательность работ и критерии выхода

### Этап 1. Один корректный цикл действий

Рабочие места: `agents/loop.py`, `task_loop.py`, `config.py`, `cli.py`, `llm/orchestrator.py`.

- Передавать approval_callback через настоящий интерфейс Orchestrator.
- Ввести единый ToolResult: outcome, payload/error, verification и accounting.
  Записывать каждый исход, включая policy denial, invalid args, timeout и rollback.
- Проверять allowlist роли в dispatcher; согласовать доверие к проекту и явное право на запись.
- Отсутствие результата проверки не считать PASS; различать syntax-only, tests-passed, tests-not-run.
- Проверять выполненное изменение относительно задачи, а не только финальный текст модели.
- Исправить запуск task без сохранённого индекса; включить планирование в общий учёт вызовов.

Критерий выхода: integration tests с реальным Orchestrator + scripted backend и настоящими tools,
не только FakeOrch. Проверить deny/error/no-edit/rollback и успешную правку.
Шаг не получает done, если обязательное изменение/проверка отсутствует либо завершилось ошибкой.

### Этап 2. Надёжная транзакция изменения

Рабочие места: `tools/edit_node.py`, `read_node.py`, `undo.py`, `verify.py`, `tree/builder.py`.

- Изолированная рабочая копия задачи; основной пользовательский checkout не служит черновиком агента.
- Перед edit сверять project identity и expected content hash; обнаруживать внешние изменения.
- После edit обновлять дерево, ranges, aliases и evidence context до следующего tool call.
- Представлять многофайловую правку как changeset: предварительная проверка, применение, проверка, commit/rollback состояния задачи.
- Добавить контролируемый patch fallback для imports/config/new files; AST остаётся способом адресации.
  Rename символа и его callers — отдельная операция/сценарий, нынешний same-name replacement её не реализует.
- Undo привязать к проекту, версии и активному changeset; не затирать более поздние пользовательские правки.

Критерий выхода: две последовательные правки со сдвигом строк, multi-file rename, конфликт с внешней
правкой, неуспешные тесты и авария процесса оставляют восстановимое и объяснимое состояние.

### Этап 3. Изоляция и устойчивое выполнение

- Общий SourceStore для read/materialize/edit с containment, symlink policy, hash checks и redaction.
- Проверять task_id/edit_id и project scope перед доступом к persistence.
- Запускать тесты/инструменты в ограниченной среде с контролем FS, сети, времени и process tree.
  Для первой версии выбрать и документировать одну поддерживаемую среду; затем проверить Windows отдельно.
- Task lifecycle: сохраняемые переходы pending/running/paused/cancelled/failed/done,
  фактическая остановка cancel, checkpoint resume с проверкой исходников и запрет слепого повтора edit после crash.
- Budget проверить перед каждым model call, включая planner/replanner/repair; unknown cost имеет явную политику.
  Проверять лимиты также на успешном пути. Для параллельных задач нужны reservations.

Критерий выхода: тесты на отмену, crash/restart, повторную доставку, исчерпание бюджета,
попытку записи вне workspace и запрещённый network access. Права не зависят от послушания LLM.

### Этап 4. Измерить реальную пользу

Собрать пилотный набор 30–50 реальных ограниченных задач на нескольких Python-репозиториях:
вопросы, RU/EN поиск, bugfix, изменение сигнатуры/callers, конфиги, негативные задачи.
Часть оставить закрытой для настройки. Это предложенный объём пилота, не статистическое доказательство production SLA.

Сравнивать при одинаковых модели, задачах, исходных версиях и лимитах:
обычный поиск/минимальный agent baseline; BM25; BM25+graph; затем dense+RRF/reranker.
По возможности отдельно выключать critic/refiner, чтобы измерить их вклад и стоимость.

Метрики: independently verified task success, regressions, неверный отчёт об успехе,
ручные исправления, input/output tokens, полная стоимость с retry и неудачами,
стоимость на успешную задачу, median/p95 latency, индексирование и память на больших репозиториях.
Для retrieval — recall@budget и попадание всех необходимых узлов, включая RU;
для ответов — проверяемые code quotes/line ranges и корректное признание нехватки данных.

Критерий выхода: сырые отчёты с commit/model/config и независимыми проверками; выбранные до эксперимента
пороги для пилота. Экономия принимается при сохранении качества относительно baseline.
Числа MRR из маленьких fixtures не заменяют task-success benchmark.

### Этап 5. Backend protocol и пилотный релиз

- Общие типы сообщений/tool calls/tool results и backend capability flags.
  Native tools для поддерживающих backend, text-JSON fallback для остальных.
- Native transport не заменяет policy, validation и ограничения исполнения.
- Locked/tested dependencies; CI на поддерживаемых OS/Python; wheel build -> clean install -> smoke/fixture tests.
- Схема и миграции persistence, structured logs, ограничения artifact retention, offline doctor и понятные ошибки.
- Пилот на собственных рабочих задачах с регистрацией каждого сбоя; TUI добавлять при доказанной UX-потребности.

Для командного сервиса отдельно: identity/authorization по workspace, изоляция пользователей и ключей,
ограничения concurrency/rate/cost, очередь задач, TLS termination и эксплуатационные процедуры.
Один общий API key не превращает local CLI в готовый multi-tenant сервис.

## Место encoder и multi-agent

Dense retrieval можно испытывать после фиксации evaluation baseline; он не зависит от завершения TUI.
Начать с заменяемого Encoder interface и подходящего готового embedding baseline.
Сравнить atomic-core как отдельный исследовательский вариант по качеству, памяти, latency и стоимости поддержки.
Generative checkpoint, размер 250M и формат safetensors сами по себе не определяют качество embeddings.

Multi-agent — после надёжного single-agent changeset, budget и cancellation.
Он имеет смысл при измеренном выигрыше на разделимых задачах и определённой модели владения файлами.
Несколько ролей одной модели не дают независимой проверки автоматически.
