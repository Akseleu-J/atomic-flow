## Conclusion

Docker can be removed from ordinary installation, indexing, retrieval, planning, source editing and much local development. Removing it from untrusted code execution requires another actual OS boundary. Setting the existing default to `local` would remove filesystem/network confinement and reliable process ownership, so that is not an equivalent migration.

Recommended product architecture: small Docker-free Python core; execution capability negotiation; explicit trusted-local execution; native sandbox adapters where proven; optional remote execution and optional OCI adapter. On this 3.4 GiB Windows machine, start with the core and reviewed trusted-local checks; use an existing remote runner for untrusted execution until Windows native confinement is independently accepted. Docker may remain in CI and on remote hosts without becoming an end-user prerequisite.

## Current implementation strengths

- Docker checks use no network, nonroot identity, read-only root, dropped capabilities, no-new-privileges, process/memory/CPU limits and bounded output (`src/atomic_flow/agents/execution.py:133-148`). No Docker socket is mounted. This is a useful baseline, not evidence of escape resistance against arbitrary hostile workloads.
- Checker bootstrap imports the installed checker before project code (`execution.py:62-89`); private admitted workspaces prevent ordinary test writes from publishing (`execution.py:100-111`). Copies and worktrees do not restrict host access.
- Jobs journal preparation before launch, use an isolated worker import bootstrap, and retain unknown effects rather than retrying (`src/atomic_flow/jobs.py:231-302`). Docker recovery uses immutable container IDs (`jobs.py:383-399`).
- Remote submissions bind source, image and request/result identities and avoid replay after an uncertain response (`src/atomic_flow/remote.py:234-297`). Workers are trusted single-owner hosts; hashes do not attest the host.
- Base dependencies are small and encoder/API integrations are optional (`pyproject.toml:12-20`). Docker is already absent from base Python package dependencies.

|---|---|---|---|---|
| Core without code execution | Supported in principle; installed-wheel gate open | Supported in principle; installed-wheel gate open | Not currently CI-verified | First release path. | OCI adapter | Linux VM/desktop layer usually still needed for this Linux image | Existing Docker; Podman would need explicit compatibility checks | Linux VM layer needed for this Linux image | Optional backend. Linux: bubblewrap provides namespace construction, not a complete security policy; the wrapper determines mounts, process visibility, networking and terminal isolation. Review policy and dependency versions independently. [Upstream bubblewrap documentation](https://github.com/containers/bubblewrap/blob/main/README.md). Landlock can reduce ambient filesystem/network rights without privilege, but restrictions depend on the detected ABI; older supported kernels have narrower controls. Probe features at runtime and fail closed for required controls. Use network namespace denial for a no-network contract rather than assuming every deployed Landlock ABI blocks every protocol. [Linux 6.12 Landlock documentation](https://www.kernel.org/doc/html/v6.12/userspace-api/landlock.html). Cgroup availability/delegation and user namespace policy must also be probed, not inferred from distro name.

Windows: Job Objects group processes, impose resources and support kill-on-last-handle-close, but security limits are separate process controls. Launch suspended, attach before resume, disallow ordinary breakaway, verify nested-job compatibility and own the handle lifecycle. This is process containment, not file/network isolation by itself. [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). Evaluate AppContainer for actual filesystem/network/process restrictions and a narrowly provisioned runtime. The higher-level Win32 app isolation packaging route is currently documented as preview with Windows 11 24H2+ requirements, so it is not a universal Python CLI deployment assumption. [Microsoft Win32 app isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/app-isolation-overview).

macOS: official App Sandbox requires an entitled application/helper packaging design; embedded command-line tools inherit the containing app's sandbox. This is extra packaging/compatibility work for a pip-distributed CLI, not a one-line subprocess flag. Prototype a signed helper/XPC path and verify permissions for dynamic Python runtimes and target dependencies. [Apple App Sandbox](https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox), [Apple sandbox inheritance](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html). Do not make an unverified private/deprecated sandbox mechanism a production foundation.

Native isolation applies to the executed process tree. Host Python plugin factories, hooks, LSP/MCP executables and credential consumers remain trusted host components unless separately moved behind an isolation boundary. Replacing the check executor does not sandbox those capabilities automatically.

## Migration plan and measurable gates

1. **Freeze execution contract and package acceptance.** Define `ExecutionRequest`, `ExecutionRequirements`, `ExecutorCapabilities`, owned execution handle and typed `ExecutionResult`. Capabilities include read/write roots, external network, credentials, process/IPC boundary, CPU/memory/PID/time/output limits, dependency/runtime identity, cancellation and crash cleanup. A backend can meet requirements or refuse; it cannot weaken them. Preserve existing tool permission, snapshot, journal, source hash and unknown-effect gates. Add clean-wheel CI before executor migration so source-tree imports cannot mask distribution failures.
2. **Make core genuinely independent.** No Docker discovery/build/start during core import, installation, index, retrieval, planning or source-only editing. Add a no-Docker/no-network smoke job. Separate framework package, check tooling extra and target-project environment. Determine the executor before a task incurs model spending for required checks; unavailability is a technical preflight error. Review and approval of trusted-local execution remain host-owned and scoped.
3. **Strengthen trusted local lifecycle.** Windows Job Object ownership first; Linux owned process/resource mechanisms where available. Add parent-success descendants, detached descendants, cancellation, timeout, worker death, pipe retention, output-limit and concurrent-admission tests. Measure actual resource usage. This removes accidental process leaks; it does not claim adversarial local isolation.
4. **Offer remote optional execution.** Reuse source/result binding and reconcile-by-request-ID; deploy a single-owner endpoint, pinned runtime, synthetic secret exclusion, reverse proxy TLS, request authentication, capacity metrics and journal-aware GC. Prove unknown submit/cancel handling under connection loss without resubmission. Client install and normal usage must require no Docker or VM.
5. **Prototype one native backend at a time.** Linux is the most direct daemon-free path; Windows is high value for this user but has runtime/ACL engineering costs; macOS requires separate signed-helper feasibility. Select according to acceptance evidence, not equal feature labels. Preserve OCI as optional compatibility/reference backend until native parity is measured.
6. **Production release gate.** Package installed outside repository on Windows/Linux/macOS; documented supported Python/dependency versions; API/core/worker extras independently tested; multiple real target repositories with their own dependencies; repeated source-only and edit/check/publish cycles; bounded resource and storage behavior; cancellation/recovery after host and worker crash; immutable evidence manifest tying wheel, source, environment, tests and runtime. Native isolation failures are release blockers for that backend, not for Docker-free source-only core.

Native security acceptance matrix: denied reads of synthetic host/home credentials; denied writes outside staged roots; read-only profile writes fail; IPv4/IPv6/TCP/UDP/DNS/loopback/Unix or named-pipe access policy; inherited file descriptors/handles; symlink/junction/race probes; child/grandchild/parent-exit cleanup; process enumeration/signals/IPC; fork/process/memory/output/disk exhaustion; zero-test and checker shadowing regressions; source confidentiality; denied capability does not trigger local fallback. Run hostile/resource tests only on disposable dedicated runners with controlled limits. A passing matrix supports the stated threat model, not an absolute security guarantee.

## Verification limits

This pass performed source and configuration inspection plus official-source research. It did not rebuild/install a wheel, repeat unit tests, run hostile processes, measure sandbox overhead or test OS adapters. Existing real Docker CI demonstrates the current selected boundary tests for its recorded source; it does not establish native equivalence, cross-platform release quality, arbitrary repository environments or live edit success. No production-ready or unlimited-security claim is warranted.

An additional static detail strengthens the Windows lifecycle finding: `_kill_tree` ignores the return code of `taskkill` (`src/atomic_flow/agents/execution.py:158-160`). Only launch/timeout exceptions set `uncertain`; a nonzero helper exit is not itself converted to unknown cleanup. Bounded reader joins (`:283-289`) can detect inherited open pipes but cannot prove absence of descendants that close or redirect their streams. These are code-path findings, not a new hostile-process reproduction. The accepted replacement must verify owned process termination rather than treating parent exit, empty pipes or helper invocation as proof.

Official sources were reopened during the resumed pass. Microsoft still labels the higher-level Win32 app isolation packaging feature preview and lists Windows 11 24H2+; this must not be confused with the older AppContainer primitives. Microsoft Job Objects also explicitly describes child creation exceptions and separate security controls, so a Job Object is a lifecycle building block, not complete confinement of arbitrary hostile code. Linux 6.12 Landlock is an intentionally pinned documentation baseline, not a claim about the newest kernel: runtime ABI detection determines the rights actually available. The Apple archived entitlement documentation was readable and confirms signing/inheritance design; the newer App Sandbox page exposes a JavaScript/Markdown endpoint that this research tool did not retrieve. The macOS proposal therefore remains a design candidate requiring current SDK and signed-helper validation.
