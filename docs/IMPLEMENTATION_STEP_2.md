# Пакет 2: актуальные исходники и staged changesets

Дата: 16 октября 2026. Локальная реализация поверх HEAD `820fc83` и пакета 1.
Изменения не закоммичены и не опубликованы. Production-план целиком ещё не закрыт.

## Что реализовано

| Узел | Поведение |
|---|---|
| agents/source.py | общий confined path, запрет symlink/junction, чтение по ожидаемому SHA-1 индекса, сравнение перед replace |
| ToolContext | хранит стартовые hashes, revision и evidence; после edit полностью пересобирает дерево и ActivationIndex, сохраняет старые aliases без повторного использования удалённых ID |
| read_node | проверяет hash при каждом чтении, маскирует распознаваемые секреты, поддерживает явные страницы offset/next_offset; evidence содержит только возвращённые страницы |
| edit_node | защищён от устаревшего источника, сохраняет CRLF/BOM, откатывает и при исключении verifier; повторно проверяет записанные bytes после проверки |
| UndoStack | обязательный whole-file backup, project binding, before/after hash, отказ при чужом проекте/третьей версии, отметка undone на диске |
| Orchestrator | пересобирает materialized context после edit; critic/grounding видят текущую ревизию; прочитанные tool-узлы становятся допустимыми evidence/citations |
| tree.builder | исключает private ATOMIC_FLOW_HOME даже если тот находится внутри проекта; backups/runtime не становятся источниками контекста |
| ChangeSet | отдельная копия проекта, журнал baseline/approved hashes, workspace checkpoint перед шагом, проверка конфликтов до/во время переноса |
| TaskRunner | все шаги/pytest идут в workspace; ошибочный шаг восстанавливается до replan; исходный проект изменяется только после успешного завершения всей задачи |
| Task persistence/CLI | changeset_id, проверка Task ID, запрет небезопасного legacy/unknown resume; offline --recover без модели |

Настройки доверия и prompts берутся от исходного проекта, а исходники для выполнения — из workspace.
Шаги marked done до публикации означают «проверены в workspace». Статус всей задачи done сохраняется
только после успешного переноса. Незавершённая запись Task JSON после завершённого переноса не приводит к повторению edits:
runner проверяет published manifest и завершает регистрацию задачи.

## Контракт changeset

1. Копируем managed-файлы текущего проекта и сохраняем исходный manifest. Незакоммиченные исходные правки входят в baseline.
2. Перед шагом сохраняем checkpoint workspace и разрешённые hashes.
3. Applied tool results привязывают разрешённый путь к конкретным проверенным bytes.
4. Если шаг провалился — восстанавливаем workspace checkpoint, включая удаления новых файлов, затем разрешаем replan.
5. Перед переносом сверяем исходный manifest и проверяем, что workspace изменён только разрешёнными версиями файлов.
6. До первого replace сохраняем журнал намерений и backups. При обычной ошибке переноса возвращаем свои изменения.
7. При прерывании процесса --recover использует before/after hashes. Третью версию файла сохраняет и отмечает recovery_conflict.

Никаких Git commit/reset операций transaction не выполняет. Dirty исходные файлы не сбрасываются.
После успеха и восстановления обновляется индекс проекта. При ошибке записи индекса исходники также откатываются;
если индекс остался устаревшим, hash guard не позволяет читать старые срезы как актуальные.

## Проверки и свидетельства

- Штатный pytest: **142 passed, 2 skipped**, 19.34 s — `validation/step2-release.txt`.
- Дополнительные root v3 tests: **17 passed**, 0.14 s — `validation/step2-root-v3.txt`.
- Ruff по всем изменённым runtime/test-файлам и compileall src: PASS.
- git diff --check: PASS. Git предупреждает о будущей нормализации LF/CRLF для undo.py, без whitespace errors.
- Проверки используют scripted/fake backend; реальные LLM/Kaggle запросы отсутствуют.

Ключевые сценарии:

- внешний edit между индексированием и записью; stale повторное чтение;
- две правки со сдвигом строк и прежним alias второго определения;
- исключение verifier, неуспешный matching pytest и безопасный undo;
- CRLF/BOM; длинное определение и страницы evidence;
- две реальные task-правки: успех переносит обе; провал второй оставляет исходный проект прежним;
- неподтверждённые изменения workspace и подмена bytes уже разрешённого файла;
- ошибка во втором файле при переносе; прерывание между файлами; повторное открытие журнала;
- пользовательская правка после прерывания не затирается recovery;
- восстановление CLI не вызывает make_backend;
- critic не получает старые исходники после edit; read_node вне первоначального retrieval становится evidence;
- частное хранилище внутри project root исключено из индекса.

Пропущены POSIX permissions и создание symlink без нужных Windows-привилегий.
Есть прежнее предупреждение Starlette/httpx. Linux/macOS и большие репозитории здесь не проверены.

## Как пользоваться восстановлением

```powershell
& .venv\Scripts\python.exe -m atomic_flow.cli task --show TASK_ID
& .venv\Scripts\python.exe -m atomic_flow.cli task --recover TASK_ID
```

--recover применим к publication journal в publishing/recovery_conflict либо к завершённому published состоянию.
Он не перезапускает оборвавшийся model step. Workspace и journal сохраняются для разбора.
При конфликте нужно сначала просмотреть состояния; автоматического перезаписывания пользовательской версии нет.

## Границы текущей гарантии

- Это filesystem copy, а не OS sandbox: тесты могут обратиться к сети, ключам, исходному проекту или другим путям
  через абсолютные ссылки. Для недоверенных проектов использовать после отдельного этапа изоляции исполнения.
- Multi-file replace виден сторонним читателям пофайлово. Журнал даёт восстановление после process interruption,
  а не общую атомарность ФС или гарантию при отключении питания. Нет межпроцессной блокировки конкурирующих publishers.
- Snapshot/publish исключает .git, окружения/caches, private atomic state, большинство hidden файлов.
  Это не полная копия окружения; Git-зависимые проверки и нестандартные fixtures могут потребовать адаптации.
- Workspace/checkpoint/backup copies увеличивают диск и задержку. Retention для changesets и performance на больших
  codebase пока не реализованы/не измерены. Не путать с bounded-memory storage.
- `atomic ask --approve-edits` остаётся прямой правкой с per-edit undo. Task-wide staging действует на `atomic task`.
- Старые edit backups без project/hash metadata не принимаются для автоматического undo.
- Рабочее пространство не доказывает смысловую правильность задачи. Expected outcomes и независимые acceptance checks нужны отдельно.
- Budget/accounting planner/replanner, настоящая отмена запущенного процесса и hermetic execution environment остаются в следующем пакете.
  Context budget по-прежнему не ограничивает всю накопленную tool history.
